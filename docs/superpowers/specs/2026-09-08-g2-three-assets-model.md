## 1. 目的与验收(G2)

**目的**:把 DEC-003 定的三资产目录落成可复用的模型——事实卡怎么建、知识资产与其它资产怎么分界、数据源怎么登记——让 L1~L4 各闭环直接引用,不各自发明。

**验收**:模型可被 L1~L4 复用(映射见 §5)。

## 2. 事实卡模型(Facts)

### 2.1 定位

事实卡是**唯一技术事实源**(红线1):AI 写作/问答只准引用 approved 事实卡,禁止自创技术表述;新事实未成卡前不得进正文。

### 2.2 类别(class,6 类)

| class | 含义 | 示例 |
|---|---|---|
| `product` | 产品参数 | 额定功率、循环寿命、温度范围 |
| `advantage` | 技术优势 | 效率、安全设计、运维特性 |
| `certification` | 合规认证 | CE/UL/UN38.3、并网标准 |
| `case` | 项目案例 | 部署规模、区域、效果 |
| `company` | 公司资质 | 成立、产能、出口市场 |
| `price` | 报价政策(如有) | 价格带、MOQ、条款 |

### 2.3 存放与文件

- 目录:`content/facts/<class>/F-<CLASS>-<nnn>.md`(CLASS 为大写,如 `content/facts/product/F-PRODUCT-001.md`)。
- 编号规则:`F-<CLASS>-<nnn>` 全局唯一、顺序递增;作废不重号(编号即审计锚)。
- 卡片创建于 M1.2(录入模板 + 工具);本 spec 只定 schema。

### 2.4 单卡结构(录入模板 = 此骨架)

```yaml
---
id: F-PRODUCT-001
class: product
title: 工商储一体柜 额定功率 100kW
status: draft            # draft → approved → obsolete
reviewer: ""             # 业务负责人
reviewed_at: ""          # YYYY-MM-DD
markets: [EN, DE]
keywords: [工商储能, 一体柜, 100kW]
source: ""               # 素材/来源登记条目 或 repo 路径 + 页码/章节
glossary_terms: []       # 关联术语,引用 content/glossary 条目
related_facts: []        # 相关卡编号
---
## zh
<源语事实内容(默认中文,主源)>
## en
<已核验英文译文>
## de            # 按需;无则省略该节
<已核验德文译文>
```

### 2.5 字段规约(规则)

| 字段 | 规则 |
|---|---|
| `id` | 必填,唯一,永不复用 |
| `status` | 仅 `approved` 可被正文引用;`obsolete` 由人置,禁继续引用;`draft` 中间态 |
| `reviewer` / `reviewed_at` | 进 `approved` 前必填(红线3 人审在内容层,卡核验人=业务负责人) |
| `source` | **必填**;无来源引用不得成卡(溯源锚,红线1)。指向素材/来源登记条目(形态由 L1 M1.1 定)或 repo 文件路径 + 位置 |
| `title` / body | 一条卡一个**原子、单义**事实或紧密同源的一组;避免一句多义 |
| `markets` / `keywords` | 驱动检索与选题匹配;多语言正文只给 `markets` 覆盖到的语言 |

### 2.6 引用与溯源纪律

- 正文/内容稿引用卡片 = 引用编号 `[F-PRODUCT-001]`,含来源可回查(总纲红线1)。
- 卡内容更新(参数变更/发现错误)→ 改卡 + 更新 `reviewed_at` 重新核验;旧版靠 git 历史留存。
- 卡与卡互链、卡与术语互链(§2.4 字段),保证技术表述语言一致。

## 3. 知识资产边界规则(Knowledge)

> 本次**只立边界规则**,不建 `knowledge/` 原文库——原文收集/治理归 **L4.1**(总纲 P3)。

### 3.1 定义

知识资产 = 权威**原文,文档级**,不可由 AI 改写:
产品手册、技术白皮书、合规认证文件、标准/法规、历史 FAQ、报价政策原文。

### 3.2 四资产判据与流向

```
知识资产(knowledge/,原文=溯源底,文档级)
   │  提炼(人/AI 起草 → 人核验)
   ▼
事实卡(content/facts/,原子技术表述=唯一引用源)   ←── 红线1 只引用这里
   │  引用
   ▼
内容稿(content/pipeline/,对外)                    ←── 红线3 人审后发布
数据资产(data/,行为/交易:询盘/线索/画像)  ←── 与知识/内容**正交**,不承担技术表述
```

### 3.3 边界判据(某资料是否归知识资产)

同时满足:① 权威来源(手册/白皮书/认证/公司发布物/标准);② 有责任主体;③ 可版本化(文本,能 git 追踪)。满足即登记为"待治理原文"(L4.1 前不建库,见数据源登记表"知识原文"行)。

### 3.4 反哺纪律

业务方给出新技术事实/修订 → 一律先落成事实卡(带来源)→ 才可进正文;不绕过卡直接改内容稿(与 DEC-002 变更链同构)。

## 4. 数据源登记(schema 即活文档)

登记表 schema 与已知/挂起行见活文档 `docs/discovery/2026-09-08-g2-datasource-registry.md`,本 spec 不重复清单。要点:

- 登记**不替代** G1《现状与对接清单》——那是"现状+遗留(O-list)",这是"面向数据接入的逐源登记";两表互链,新事实按 DEC-002 先入 G1 清单再回填本表。
- O1/O2 相关行(CRM/ERP、渠道账号 API)挂起"待确认 O#",不阻塞其它资产模型。

## 5. 验收映射(可被 L1~L4 复用)

| 闭环 | 本 spec 供其使用 |
|---|---|
| L1 | M1.2 录入模板按 §2.4;M1.3 首批卡按 §2.2/§2.3;回流登记字段口径引 §4 |
| L2 | 数据源登记表 → 接入清单(L2.1) |
| L3 | 画像/评分数据来源 → 登记表(L3.1) |
| L4 | 治理范围 = §3 边界规则(L4.1);事实卡供可溯源作答(L4.2) |

- [x] 事实卡 schema 可直接驱动 M1.2 录入模板(§2 字段规约完备)。
- [x] 知识边界规则可作 L4.1 范围(§3)。
- [x] 数据源登记 schema+已知行就绪,未知行挂起不阻塞(§4 + 活文档)。
- [x] 与 DEC-003 目录边界无冲突;不给各闭环加未定 schema 负担(YAGNI:类别级扩展字段后置)。

## 6. 开放问题(不阻塞)

- 事实卡是否需要类别级附加字段(如 `product` 卡的标称参数表)→ 首批卡(M1.3)用真数据试出再补,不进本 v1。
- 素材/来源登记的具体形态 → L1 M1.1 spec 定,本 spec 只要求事实卡能指向它。
