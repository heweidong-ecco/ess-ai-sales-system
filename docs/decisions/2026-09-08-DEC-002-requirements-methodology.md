# 决策记录:DEC-002 · 需求方法论(是否引入 PRD)

- 日期:2026-09-08
- 状态:已采纳(业务方裁定:"不引入 PRD")
- 关联:`系统总纲.md`、`docs/ROADMAP.md`、各闭环 spec、DEC-001

## 裁定

**本项目不引入独立的 "PRD" 产物。** 需求层只由两层构成:

```
系统总纲.md   = 最高需求层(全系统 Program Charter + 轻 PRD):业务边界/飞轮/闭环/路线图/红线
各闭环 spec   = 该闭环的"需求 + 验收 + 设计"合一文档(docs/superpowers/specs/)
               内含:范围(做/不做)、验收、红线、开放问题
```

## 理由

1. 独立 PRD 与 spec 会形成**双份维护**:需求改了改哪份?易漂移
2. spec 已含"范围 + 验收"字段(见 L1 spec §2/§8),"需求视角"并不缺失
3. 与业务方对齐的动作已由 **ROADMAP 验收列 + G1《现状与对接清单》**承担,不需要再造文档形态

## 需求可追溯链(新需求/变更一律走此链)

```
总纲 §2 指标 ──► ROADMAP 节点"验收" ──► 该闭环 spec"验收" ──► 实现 ──► 验证(挂指标)
      ▲              │                                        │
      └──────── 冲突先回总纲对齐 ───────────────────────────────┘
```

## 业务输入的入口约定

- 业务侧新事实/答案 → 一律进 `docs/discovery/2026-09-08-g1-inventory.md`《现状与对接清单》
- 新事实需要改 spec 时 → 先回总纲/ROADMAP 对齐,再改 spec(不静默改)
