## 背景

总纲 §6 只给高层五层草案,注明"分层专题另文详谈"。G3 把该专题**定稿**为可遵循基线——既要"与 §6 无冲突",又要"能指导各闭环"。

**贯穿主张:分层 = 职责边界 + 依赖方向 + 升级触发,不是多仓库/多服务。** 物理上一个 git 仓库即全系统,Claude Code 即运行时;某一层片段出现量化信号后,才升级成真实服务,且每步独立决策。

## 裁定

### C1 · 物理基座:单仓库即系统

- 一个 git 仓库承载全部资产(spec/plan/决策/内容/知识/数据)。
- 分层体现在**目录职责 + 依赖方向 + 生命周期**,不在拆服务。
- 理由:git 提供版本化、diff、审计与回滚(红线4 审计前置);内容/知识/数据皆文本可人审;闭环用独立 spec + worktree 隔离即可,无需多仓库。
- 反悔成本:低——升级是"某子目录换成 DB/服务",仓库边界不变。

### C2 · 五层实例(沿 §6 五层,逐层实例化)

| 层(§6 权威) | 职责一句话 | 仓库实例(现选) | 升级触发(到点再开 DEC) |
|---|---|---|---|
| **应用与角色层** | 各角色各自的使用界面与 Agent | 无独立 UI:各角色面对「仓库工作台 + Claude Code 会话」。审校者看 `content/tracker.md` 放行;内容执行者按 `sop/` 在会话内执行;销售消费已发库/一线提问变选题 | 出现"非 Claude Code 用户"需自取数据/操作 → 先静态导出/仓库页面(薄界面),不动辄建系统 |
| **闭环编排层** | 各闭环工作流编排(触发→执行→人审→回流) | 每闭环 = 一份 spec(DEC-002)+ 仓库 pipeline 目录 + tracker 状态流(草稿→审校→待发→已发);触发默认**人起头**,Claude Code 执行 | 需无人值守/定时/外部 API 拉取(L2.2)→ 引入**最小调度**(候选:cron / GitHub Actions / Claude Code schedule);此前不跑常驻服务 |
| **AI 能力层** | 模型调用 / Agent / 工具 / 检索 | Claude Code(project 作用域 superpowers)= 唯一模型运行时;每闭环提示词模板进 `sop/`;**L4 前无 RAG/向量库**,前检索 = 事实卡编号引用 + grep/结构化检索 | 工具/MCP 只在具体闭环真需要时接(如 L2 抓取、L4 检索);**向量库决策放 L4 spec**,触发=知识资产需语义召回 |
| **资产与数据层** | 数据集成、内容/知识资产库、画像/评分存储 | 三资产目录:`content/`(facts/glossary/keywords/pipeline/tracker/monthly-review)+ 预留 `knowledge/`(L4)、`data/`(L2/L3)。事实卡 = 唯一技术事实源(红线1)。schema 细节归 **G2**,本层不给 schema | 事实卡或线索 > ~500 条、或需联表/权限查询 → 该子目录升级 **SQLite**(单文件零运维);L4 知识资产成熟后才谈检索底座 |
| **系统与合规层** | 渠道/CRM-ERP 对接;权限、审计、合规、模型治理 | 分支/评审纪律 + 人审 gate(对外产物必经人放行);账号/密钥/API 凭证**永不入库**(.gitignore + 环境变量);git history = 审计;红线1 模型治理由事实卡承载。对外集成统一"适配器"接口(导入/导出 + 凭证),未到位一律人工回流登记(L1 C4 已是此形态) | 多人协作冲突 → 细化权限/评审;多系统回写 → 再评估凭证与审计粒度 |

> 依赖方向(只可往下依赖,不可反向):应用与角色层 → 闭环编排层 → AI 能力层 → 资产与数据层 → 系统与合规层。闭环(spec)跨层编排,但实现分层、单向依赖。

### C3 · 层间接口约定

- 层间不定义"API/服务接口",定义**仓库路径 + 文档引用**:
  - 下层产物 = 文件/目录 + schema(G2 起逐步给);上层通过 spec/决策**引用路径与编号**取用(如写作引用 facts 编号)。
  - 人审 gate、发布 checklist 落在 `sop/` 与各闭环 tracker,是层间唯一的"硬接口"。
- 任何闭环 spec 若引入仓库之外的运行体(DB/服务/定时/外部 API),必须先对表本记录触发列,并把该升级点写成 DEC。

### C4 · 三资产目录约定(边界;schema 归 G2)

| 资产 | 路径 | 消费方 |
|---|---|---|
| 内容资产 | `content/` | L1 生产/人审/回流 |
| 知识资产(预留) | `knowledge/` | L4(原文 + 治理,规则归 G2/G2 后) |
| 数据资产(预留) | `data/` | L2 线索 / L3 画像评分 回流 |

- 事实卡是**唯一技术事实源**;技术表述只准引用 Facts(红线1 承载)。
- L5 赋能横切:`sop/`(SOP/模板/提示词)随每个闭环沉淀,见总纲 §5 L5。

### C5 · 升级策略(通用信号)

任一信号出现,即对相应层片段单独开 DEC,不整体换代、不推翻本定稿:

1. **规模**:事实卡/线索 > ~500 条,或单目录文件检索变慢;
2. **时效**:有无人值守/定时/实时响应要求(L2 抓取、L4 客服);
3. **并发**:多人写冲突频繁、需要锁/事务;
4. **权限**:跨角色隔离/审计粒度需求超出 git 可表达;
5. **外部回写**:需对 CRM/ERP/渠道做自动回写。
